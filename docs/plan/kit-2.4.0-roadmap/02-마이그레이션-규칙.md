# 02. 마이그레이션 규칙 — 기존 flat → hierarchy 전환 가이드

> **한 문장 요약**: 기존 archive(OLP/DASH/DASH3)는 **강제 재구성 금지** 하되, 새로운 Epic 을 "명명된 뷰(view)" 로 만들어 소급 연결할 수 있다. 마이그레이션은 **선택사항** 이며 데이터 손실은 0.
>
> **비유**: 도서관의 책들을 새 장르 분류에 맞춰 **다시 라벨을 붙이는 작업**. 책 자체는 그대로 두고, **라벨만 새로 추가** 한다.

---

## 1. 핵심 원칙

### 원칙 1: 기존 데이터 불변성
- `archive/index.md` / `archive/{slug}/` / `ideas/backlog.md` / `features/active/*` 의 **기존 파일 수정 금지**
- Epic 연결은 **신규 파일 추가** (`epic-binding.md`) 또는 **인덱스 컬럼 추가** (null 허용) 로만

### 원칙 2: Opt-in 전환
- Epic 에 속하지 않는 기존 Feature 는 그대로 유지
- **"이 Feature 는 어느 Epic 에?"** 질문이 명확한 Feature 만 소급 연결

### 원칙 3: 점진적 전환
- 한 번에 모든 Feature 를 Epic 에 연결하지 않음
- **PoC 1 Epic (dash-preview Phase 4)** 로 시작 → 성공 시 archive 재구성 검토

### 원칙 4: 가역성
- Epic 연결은 `00-context/08-epic-binding.md` 파일 삭제로 즉시 해제 가능
- `backlog.md` / `archive/index.md` 의 `epic_id` 컬럼도 null 로 복귀 가능

---

## 2. 3 가지 마이그레이션 시나리오

### 시나리오 A: 새 Epic + 새 Feature (PoC, 권장)

**언제**: 차기 Feature 부터 Epic 도입
**난이도**: 낮음 (신규 Feature 는 처음부터 Epic 태그)

**절차**:
```
1. /plan-epic "OPTIC Landing" → EPIC-20260422-001 생성
2. /plan-idea "새 기능" --epic=EPIC-20260422-001 → IDEA 자동 연결
3. 이후 /plan-screen → /plan-draft → ... → /plan-archive 정상 진행
   (Epic 연결은 IDEA 단계에서 한번 결정 후 유지)
```

**리스크**: 없음 (신규만)

---

### 시나리오 B: 기존 active Feature 를 새 Epic 에 소급 연결

**언제**: 현재 `features/active/` 에 있는 Feature 를 묶고 싶을 때
**난이도**: 낮음

**예시**: dash-preview-phase4 (가칭) 가 active 상태일 때 Epic 연결

**절차**:
```
1. Epic 생성: /plan-epic "OPTIC Landing" → EPIC-20260422-001
2. Epic adopt: /plan-epic-adopt EPIC-20260422-001 dash-preview-phase4
   → 자동 작업:
     - .plans/features/active/dash-preview-phase4/00-context/08-epic-binding.md 생성
     - .plans/epics/10-planning/EPIC-20260422-001/01-children-features.md 에 행 추가
     - .plans/ideas/backlog.md 의 해당 IDEA 행에 epic_id 컬럼 채움
3. (선택) Epic 의 PRD 에 해당 Feature 의 REQ 를 인용 방식으로 포함
```

**리스크**: 낮음 (가역 가능, 파일 삭제 또는 epic_id null 화)

---

### 시나리오 C: archived Feature 를 새 Epic 에 소급 연결

**언제**: archive/OLP, archive/dash-preview, archive/dash-preview-phase3 를 "OPTIC Landing" Epic 에 모두 연결하고 싶을 때
**난이도**: 중간

**절차**:
```
1. Epic 생성: /plan-epic "OPTIC Landing 제품 라인" --status=archived
   → EPIC-20260422-099 (archived Epic, 기존 완료작 묶기용)
   → .plans/epics/90-archive/EPIC-20260422-099/ 로 바로 생성

2. Epic children 명시:
   - .plans/epics/90-archive/EPIC-20260422-099/01-children-features.md 에
     3 Feature 나열 + 각 archive 번들 링크

3. archive/index.md 인덱스에 epic_id 컬럼 추가:
   | Key | Slug | ... | Epic |
   | OLP | optic-landing-page | ... | EPIC-20260422-099 |
   | DASH | dash-preview | ... | EPIC-20260422-099 |
   | DASH3 | dash-preview-phase3 | ... | EPIC-20260422-099 |

4. (선택) 각 archive 번들의 ARCHIVE-{KEY}.md 상단 메타에 Epic 추가
   (단, 번들 자체는 수정하지 않고 Epic 쪽에서만 참조하는 안이 원칙 1 준수)
```

**리스크**: 중간 — archive 번들 자체는 불변이므로 "아카이브 쪽에서는 Epic 모름" 상태 허용 필요. Epic 문서가 one-way 참조.

## 3. 마이그레이션 매트릭스 (의사결정 표)

| 상황 | 권장 시나리오 | 대안 |
|---|:---:|---|
| 차기 신규 Feature | **A (PoC)** | — |
| 현재 active 이고 아직 Epic 없음 | **B (adopt)** | 그대로 독립 운영 (Epic 필요 없으면 skip) |
| 이미 archived 이고 단독 | **연결 안 함** | C (Epic 에 참조만) |
| archived + 제품 라인 명확 (예: OPTIC Landing 3건) | **C (archived Epic 소급)** | 그대로 두고 Epic 없는 legacy view 유지 |
| 현재 active + 이미 다른 Epic 에 연결 | Epic 이동: `/plan-epic-move {feature} {new-epic}` | 수동 binding.md 수정 |

## 7. 데이터 검증 스크립트 (선택, 후속 IMP)

마이그레이션 전/후 데이터 정합성 검증:

```bash
# .claude/scripts/epic-validate.js (후속)
1. 모든 Feature Package 를 스캔
2. 각 Feature 의 08-epic-binding.md 존재 여부 체크
3. binding 이 있으면 Epic 의 01-children-features.md 와 cross-reference
4. 불일치 발견 시 경고:
   - Feature A 는 Epic X 에 바인딩 but Epic X 의 children 에 없음
   - Epic Y 는 Feature B 를 children 에 명시 but Feature B 는 binding 없음
5. backlog.md / archive/index.md 의 epic 컬럼도 동일 교차 검증
```

**위치 후보**: `.claude/hooks/plan-epic-integrity.js` (PreCommit 훅) 또는 스탠드얼론 CLI.

## 8. 롤백 절차

Epic 연결을 해제하고 싶을 때 (시나리오별):

### 8-1. 시나리오 A/B 롤백 (active Feature)
```bash
1. rm .plans/features/active/{slug}/00-context/08-epic-binding.md
2. .plans/epics/.../01-children-features.md 에서 해당 Feature 행 제거
3. .plans/ideas/backlog.md 의 epic 컬럼 "—" 로 복원
```

### 8-2. 시나리오 C 롤백 (archived Feature 의 Epic 소급 연결)
```bash
1. .plans/archive/index.md 의 epic 컬럼 "—" 로 복원
2. Epic 의 01-children-features.md 에서 해당 행 제거
3. Epic 자체를 제거할 경우 git mv .plans/epics/.../ trash/  (또는 그냥 archived Epic 유지)
```

**데이터 손실 없음** — 모든 변경이 추가/제거 범위 명확.

## 9. FAQ

### Q1. 왜 강제 마이그레이션을 하지 않나?
**A**: 기존 archive (OLP/DASH/DASH3) 는 이미 완료작이며, Epic 없이도 각자 독립 가치를 갖는다. 강제 재구성은 **문서 위험 (잘못된 Epic 에 소속)** 만 낳고 실익 적음. Opt-in 원칙 유지.

### Q2. Epic 없는 Feature 와 Epic 있는 Feature 가 혼재해도 되나?
**A**: 네. 완전 혼재 가능. kit 의 모든 기존 커맨드는 Epic 존재 여부를 **optional 파라미터** 로만 취급.

### Q3. 한 Feature 를 여러 Epic 에 동시 연결 가능한가?
**A**: **불가능 (설계상 1:1)**. Feature 가 여러 Epic 에 걸쳐 있다면 그 Feature 를 더 작은 단위로 분할하거나, cross-cutting Epic (예: "접근성") 을 **참조 Epic** 으로 만들고 primary Epic 하나만 binding 에 명시.

### Q4. Epic 간 의존성은?
**A**: 본 설계에서는 **Epic 간 parent-child 없음** (4단 계층 반대). 두 Epic 이 의존 관계가 있다면 Epic Brief 의 "의존 Epic" 섹션에 참조 (소프트 링크).

### Q5. "Sub-feature" 개념은?
**A**: 본 설계에서는 **도입하지 않음** (복잡도 회피). 4 Sibling Feature 로 취급. 나중에 필요 시 별도 IMP 로 추가 검토.
