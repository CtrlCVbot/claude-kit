# 01. 계층 설계 — Epic / Feature / Task 3단 구조

> **한 문장 요약**: 제품 목표(Epic) → 배포 단위(Feature) → 커밋 단위(Task) 의 3단 parent-child 관계를 명시적으로 표현하되, **Epic 은 Opt-in** (필요할 때만 사용) 으로 기존 구조와 100% 호환된다.
>
> **비유**: **도서관의 장르 → 책 → 챕터** 관계. 장르(Epic)는 여러 책을 묶는 상위 카테고리, 책(Feature)은 완결된 독립 단위, 챕터(Task)는 책을 구성하는 작은 조각.

---

## 1. 3 계층 정의

### 1-1. Epic (대) — 제품 목표 / Theme

| 속성 | 값 |
|---|---|
| **목적** | 제품 목표·방향성·중장기 Theme 을 묶는 상위 컨테이너 |
| **단위 기간** | 1~3개월 (여러 릴리스에 걸침) |
| **RICE 재평가** | 가능 (분기별 우선순위 조정) |
| **ID 규칙** | `EPIC-{YYYYMMDD}-{NNN}` (예: `EPIC-20260422-001`) |
| **파일 경로** | `.plans/epics/{status}/EPIC-{YYYYMMDD}-{NNN}/` |
| **children** | Feature N 개 (0~20) |
| **상태 전이** | `draft → planning → active → completed → archived` |
| **Opt-in** | ✅ **모든 Feature 가 Epic 에 속할 필요 없음** |

**예시**:
- `EPIC-20260422-001` "OPTIC Landing 제품 라인" (OLP + DASH + DASH3 + Phase 4)
- `EPIC-20260422-002` "AI 화물 등록 제품화" (landing 을 넘어 실제 broker 제품)
- `EPIC-20260422-003` "접근성 + 국제화 (i18n)" (여러 Feature 에 걸친 cross-cutting theme)

**필수 파일**:
```
.plans/epics/active/EPIC-20260422-001/
├── 00-epic-brief.md           # 목표 / 성공 지표 / 범위 / 기간
├── 01-children-features.md    # 자식 Feature 목록 + 순서 + 의존성
├── 02-roadmap.md              # Epic 내부 로드맵 (분기별)
├── 03-metrics.md              # 누적 지표 (LOC / tests / bundle / a11y)
└── 04-decision-log.md         # Epic 레벨 결정 (Feature 간 공통)
```

---

### 1-2. Feature (중) — 배포 단위

| 속성 | 값 |
|---|---|
| **목적** | 1개 PRD 로 완결되는 **배포 가능한 기능 묶음** |
| **단위 기간** | 1~4주 |
| **RICE 평가** | 필수 (등록 시) |
| **ID 규칙** | 기존 유지 (`IDEA-{YYYYMMDD}-{NNN}`) + Feature Package slug |
| **파일 경로** | `.plans/features/active/{slug}/` (변경 없음) |
| **parent** | Epic 0~1 개 (선택) |
| **children** | Task (기존 TASK ID 유지) |
| **Opt-in parent** | ✅ Epic 없이 독립 Feature 로 운영 가능 (기존 사용자 영향 없음) |

**주요 변화**:
- `00-context/08-epic-binding.md` **신규** (Feature ↔ Epic 연결 명시, 없으면 독립)
- PRD (`01-prd-freeze.md`) 상단에 선택적 `**Epic**: EPIC-{...}` 메타데이터 라인 추가

**기존 IDEA 와의 관계**:
- IDEA = Feature 의 **초기 단계 (inbox/screening)**
- IDEA 가 approved 되면 Feature Package 생성 (지금과 동일)
- IDEA → Feature 전이 시 Epic 선택 프롬프트 (선택적)

---

### 1-3. Task (소) — 커밋 단위 (변경 없음)

| 속성 | 값 |
|---|---|
| **목적** | 1 커밋 단위의 실행 단위 |
| **단위 기간** | 0.5~2일 |
| **ID 규칙** | `T-{AREA}-{Mn}-{NN}` (기존 그대로) |
| **parent** | Feature 1 개 + Milestone (sub-parent) |

**Milestone 은 여전히 범주 접두어** — 본 계층에서는 **Feature 내부의 "그룹"** 으로 유지 (Epic 도입으로 복잡도 증가 회피).

## 2. 계층 관계 다이어그램

```
EPIC-20260422-001 "OPTIC Landing 제품 라인"
  │
  ├─ Feature 1: optic-landing-page (archived, OLP)
  │   └─ TASK T-OLP-M1-01 ~ (과거 flat)
  │
  ├─ Feature 2: dash-preview (archived, DASH)
  │   ├─ Milestone M1: T-DASH-M1-01 ~ M1-04
  │   ├─ Milestone M2: T-DASH-M2-01 ~ M2-03
  │   └─ ...
  │
  ├─ Feature 3: dash-preview-phase3 (archived, DASH3)
  │   ├─ Spike: T-DASH3-SPIKE-01
  │   ├─ Milestone M1: T-DASH3-M1-01 ~ M1-09
  │   ├─ Milestone M2: T-DASH3-M2-01 ~ M2-09
  │   ├─ Milestone M3: ...
  │   ├─ Milestone M4: ...
  │   └─ Milestone M5: ...
  │
  └─ Feature 4: dash-preview-phase4 (planning, IDEA-20260422-001~004 → 4 Sub-feature)
      ├─ Sub-feature A: 라이트 모드 (IDEA-20260422-001)
      ├─ Sub-feature B: Mock data (IDEA-20260422-002)
      ├─ Sub-feature C: UI + 오버레이 (IDEA-20260422-003)
      └─ Sub-feature D: 정리 (IDEA-20260422-004)
```

### 중요 규칙
- **Feature ↔ Sub-feature 관계는 본 설계에서 신설하지 않음** (복잡도 회피). 대신 **Epic 안의 형제 Feature 4건** 으로 취급하되, Lane 개념을 Feature 내부 범주로 계승.
- 즉 IDEA-20260422-001~004 는 4 개 독립 Feature, 공통 parent 는 Epic "Phase 4"

## 5. ID 규칙 상세

### Epic ID: `EPIC-{YYYYMMDD}-{NNN}`
- **YYYYMMDD**: 등록일
- **NNN**: 당일 N번째 Epic (3자리, 01부터)
- 예: `EPIC-20260422-001`

### Feature ID: 기존 유지
- `IDEA-{YYYYMMDD}-{NNN}` (IDEA 단계)
- `{slug}` (Feature Package 단계, 예: `dash-preview-phase3`)

### Task ID: 기존 유지 + parent 주석
- `T-{AREA}-{Mn}-{NN}`
- parent 는 `dev-tasks.md` 상단 프론트매터에 `feature: dash-preview-phase3` + (선택적) `epic: EPIC-20260422-001` 로 명시

---

## 6. Epic 생성 기준 — "언제 Epic 이 필요한가?"

### Epic 이 **필요한** 경우 (3가지 중 하나)

1. **3개 이상 Feature 가 같은 제품 Theme**
   - 예: OLP + DASH + DASH3 + DASH4 (Phase 4) = "OPTIC Landing" Epic

2. **여러 Feature 에 걸친 cross-cutting 요구사항**
   - 예: "접근성 AA 준수" 가 여러 Feature 에 동시 적용

3. **Feature 간 명시적 순서 / 의존성 관리 필요**
   - 예: "Phase 4 = Feature A/B 병렬 → C → D 순차" 같은 실행 플랜

### Epic 이 **불필요한** 경우 (독립 Feature 그대로)

- 단독 Feature (다른 Feature 와 관계 없음)
- 소규모 bug fix / 라벨 변경
- 실험적 / 탐색적 Feature

## 7. Epic 의 라이프사이클

```
1. draft      — 아이디어만 있음, 자식 Feature 확정 전
                (`.plans/epics/00-draft/EPIC-.../`)
2. planning   — Epic Brief + Children Features 문서 작성 완료
                자식 Feature 중 최소 1건 IDEA 등록
                (`.plans/epics/10-planning/EPIC-.../`)
3. active     — 자식 Feature 중 최소 1건 구현 시작
                (`.plans/epics/20-active/EPIC-.../`)
4. completed  — 모든 자식 Feature 완료 (archive 직전)
                (`.plans/epics/30-completed/EPIC-.../`)
5. archived   — 번들화 + 인덱스 등록 완료
                (`.plans/epics/90-archive/EPIC-.../`)
```

상태 전이는 `/plan-epic-advance {id}` 커맨드 (후속 IMP-KIT)로 지원 예정.

## 8. Opt-in 원칙 — 기존 사용자 영향 0

### 기존 Feature 작성자가 알아야 할 변경
- **없음.** 기존대로 `/plan-idea` → `/plan-screen` → ... → `/plan-archive` 그대로 사용 가능.
- Epic 은 `--epic=EPIC-20260422-001` 같은 **선택 파라미터** 로만 연결.

### Epic 사용 시작하는 신규 경로
1. `/plan-epic "OPTIC Landing 제품 라인"` → Epic Brief 생성
2. `/plan-idea "라이트 모드" --epic=EPIC-20260422-001` → IDEA 가 자동으로 자식 등록
3. 기존 IDEA 를 Epic 에 소급 연결: `/plan-epic-adopt EPIC-... IDEA-...` (후속 IMP)
