# 00. 현황 분석 — 왜 계층이 필요한가?

> **한 문장 요약**: 현재 claude-kit 의 IDEA/Feature/TASK 는 모두 **flat (단일 계층)** 이라, 큰 제품 테마나 수십 개의 사용자 피드백을 묶어 관리할 방법이 없다.
>
> **비유**: 지금은 **모든 파일이 한 폴더에 뒤섞여 있는 상태**. 파일 수가 적으면 문제없지만 수십 개가 되면 "이 파일과 저 파일이 같은 프로젝트" 라는 관계를 **폴더 구조 없이 파일명만으로** 기억해야 한다.

---

## 1. 현재 kit 의 flat 구조 지도

### 1-1. IDEA 계층 (단일 평면)

**현재 구조**:
```
.plans/ideas/
├── 00-inbox/              ← 새 IDEA 등록 상태
├── 10-screening/          ← RICE 평가 중 상태
├── 20-approved/           ← 승인 상태
├── 90-archive/            ← 종료 상태
├── backlog.md             ← 모든 IDEA 인덱스 (flat 표)
└── screening-matrix.md    ← RICE 점수 인덱스
```

**관찰**:
- `00-inbox`, `10-screening`, `20-approved`, `90-archive` 는 **상태 단계** (state machine) 이지 계층이 아님
- 모든 IDEA 가 같은 레벨에서 RICE 경쟁 (큰 Theme 도 작은 라벨 수정도 동일 선상)
- IDEA-20260422-001 과 IDEA-20260422-002 가 **"같은 dash-preview Phase 4 프로젝트"** 라는 관계를 표현할 수단 없음

### 1-2. Feature Package (1:1 매핑)

**현재 구조**:
```
.plans/features/active/{slug}/
├── 00-context/
├── 02-package/
├── 03-dev-notes/
└── sources/
```

**관찰**:
- 한 IDEA = 한 Feature Package (1:1)
- 여러 Feature 를 묶는 상위 개념 없음 (예: "OPTIC Landing" 전체 시리즈 = OLP + DASH + DASH3 3 Feature)
- PRD 레벨에서만 "Phase 1 / Phase 2 / Phase 3" 같은 내부 구획을 암묵적으로 사용

### 1-3. TASK (2-depth 범주 접두어)

**현재 구조**:
```
dev-tasks.md
├── Spike TASK (T-DASH3-SPIKE-01)
├── M1 TASK (T-DASH3-M1-01 ~ 09)
├── M2 TASK (T-DASH3-M2-01 ~ 09)
├── M3 TASK (T-DASH3-M3-01 ~ 12)
├── M4 TASK (T-DASH3-M4-01 ~ 04)
└── M5 TASK (T-DASH3-M5-01 ~ 06)
```

**관찰**:
- `M1/M2/M3/M4/M5` 는 **범주 접두어** 지 parent 가 아님
- `T-DASH3-M3-10` 이 `M3 Milestone 에 속한다` 는 정보는 **ID 파싱** 으로만 추출
- TASK 간 dependency 는 `dev-tasks.md` 의 텍스트 표로만 표기 (기계 판독 어려움)

## 2. flat 구조의 한계 — 증거 기반

### 한계 1: 큰 테마 (제품 라인) 추적 불가

**예시**: `apps/landing` 의 제품 라인 전체 이력
```
OLP (optic-landing-page, 2026-04-02 archived)
  ↓
DASH (dash-preview, 2026-04-15 archived)
  ↓
DASH3 (dash-preview-phase3, 2026-04-22 archived)
  ↓
(차기)
```

세 Feature 는 모두 **"landing 의 dash-preview 제품 라인"** 이라는 공통 Theme 에 속함. 그러나 kit 에 이 Theme 을 표현할 방법이 없어:
- `.plans/archive/index.md` 에 **slug 만 나열** 된 flat 표
- 제품 라인 관점의 **누적 학습, 메트릭, 로드맵** 흩어짐

### 한계 2: 사용자 피드백 → 다수 Feature 분기 시 관계 상실

**예시** (방금 발생한 상황):
- 사용자 피드백 10 이슈
- 4 Lane 으로 그룹화 → IDEA-20260422-001~004 로 등록
- 4 IDEA 는 **"dash-preview Phase 4 후속 개선"** 이라는 하나의 목표의 자식

하지만:
- `backlog.md` 에 4 행이 **형제 (sibling) 로만** 기록
- 제목에 "(Lane 1, 단독)" 같은 **수동 태그** 로 관계 표시 (기계 판독 어려움)
- RICE 점수도 4 IDEA 독립 평가 → **전체 "Phase 4" 우선순위는 평균/합 계산 어디서 관리?**

### 한계 3: Milestone ↔ Feature ↔ IDEA 상하 관계 불명확

**dash-preview-phase3 실제 구조**:
```
IDEA-20260417-001  (단일 IDEA)
  ↓ 1:1
Feature Package: dash-preview-phase3
  ↓
Spike (1 TASK) / M1 (9) / M2 (9) / M3 (12) / M4 (4) / M5 (6) = 41 TASK
```

여기서:
- "M1 이 끝나야 M2 시작" 같은 **Milestone 간 순서** 를 kit 이 모름 (dev-tasks.md 텍스트로만)
- Milestone 별 **완료 기준 (gate)** 을 구조화된 방식으로 검증 불가
- 결과: `/dev-run` 이 Milestone 인식 없이 **TASK flat 리스트** 로만 동작

### 한계 4: DVC 검증의 한계

dev-verification-report.md §DVC-03 TASK Completion 결과:
- 41/41 TASK 완료
- 그러나 "M3 완료됐는지" 자체는 Milestone 레벨 집계가 없어 **TASK ID 접두어 파싱** 으로 역계산
- Milestone 완료 게이트 자체가 문서의 체크리스트 (수동)

## 3. 기존 IMP-KIT 들이 이미 암묵적으로 지시한 계층 필요성

| IMP-KIT ID | 요청 사항 | 계층 요구 정도 |
|:---:|---|:---:|
| IMP-KIT-015 | TASK ID 네이밍 규칙 표준화 | ⭐⭐ (parent 개념이 있으면 ID 규칙 자연스러움) |
| IMP-KIT-022 | REQ/TASK ID 프로젝트 레지스트리 | ⭐⭐⭐ (레지스트리에 parent_id 필드 있으면 설계 간단) |
| IMP-KIT-023 | decision-log.md 템플릿화 | ⭐⭐ (Feature 레벨 / Epic 레벨 로그 구분 가능) |
| IMP-KIT-027 | architecture-binding §2 자동 동기화 가드 | ⭐ (Feature 레벨 유지) |
| IMP-KIT-028 | Milestone review 사이클 decision-log 자동 기록 | ⭐⭐⭐ ("Milestone 은 Feature 의 child" 관계 명시 필요) |
| IMP-KIT-036 | Spike 1일 예산 hard cap + 이슈 승격 | ⭐⭐ (Spike 는 Feature 의 child Task) |
| IMP-KIT-038 | Spike 워크플로우 공식 skill + command | ⭐⭐ (Feature 진입 전 Gate = Feature 의 속성) |

⭐⭐⭐ 3건 = 계층 구조 도입 시 **설계가 간단해지는** IMP. 038 구현 시 본 계층과 함께 진행 권장.

## 4. flat 유지의 장점 (반대 근거 검토)

| 장점 | 실제 가치 | 대응 |
|---|:---:|---|
| 단순함 | 중 | Opt-in 도입 시 단순함 유지 (Epic 없는 독립 Feature 그대로) |
| 학습 곡선 낮음 | 중 | 기존 IDEA 작성자는 Epic 없이도 작성 가능 |
| 도구 체인 충돌 없음 | 낮음 | 본 제안은 기존 skill 수정 최소화 (Opt-in epic_id 필드) |
| 보수 비용 낮음 | 중 | 계층 도입 시 초기 학습 후에는 복잡도 증가 제한적 |

**결론**: flat 유지의 장점은 **도입 방식 (Opt-in + 단계적 3 Phase)** 으로 대부분 보존 가능.

## 5. 요약 — 계층 도입이 해결할 구체 문제

| 현재 문제 | 계층 도입 후 |
|---|---|
| 4 IDEA 가 같은 Theme 인지 "(Lane 1, 단독)" 같은 수동 태그로만 표현 | Epic 문서에 4 Feature 를 children 으로 명시 |
| archive/index.md 에 slug flat 나열 | Epic 레벨 "OPTIC Landing" 섹션 아래 OLP/DASH/DASH3 정렬 |
| Milestone 완료 게이트가 수동 체크리스트 | Feature 문서에 Milestone parent-child 정의 → 기계 판독 가능 |
| 제품 라인 누적 메트릭 (bundle / tests / reviews) 흩어짐 | Epic 대시보드에 3 Feature 누적 표시 |
| RICE 점수가 모든 IDEA 동일 선상 경쟁 | Epic 단위 (제품 목표 / OKR) RICE + Feature 단위 RICE 분리 |
