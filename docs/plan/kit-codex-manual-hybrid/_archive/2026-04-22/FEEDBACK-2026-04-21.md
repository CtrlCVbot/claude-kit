## 한 줄 결론

**설계 방향은 타당하다. 다만 Phase 0 승인용으로는 3가지 공백이 있어 "조건부 승인"이 적절하다.**

핵심 방향인 **manual-first hybrid**는 공식 Codex surface와 현 저장소 실태를 모두 반영한 합리적 절충안이다. 다만 다음 3가지 공백은 의사결정을 내리기 전에 메우는 것을 권장한다.

1. 공유 SSOT 저장 위치가 아직 "예시"로 남아 있다
2. 01에 인용된 Codex 공식 링크의 검증 기록이 없다
3. "중복"의 정량 정의가 부재하다

현재 상태로 Phase 1에 바로 착수하면 "공유 SSOT 추출"이라는 첫 단계부터 장소 결정으로 막힐 가능성이 높다.

**감사 문서의 객관적 사실 주장은 모두 정확했다.** 이 점은 설계 신뢰성에 크게 기여한다. 다만 아래 이슈들은 "사실이 맞다"와는 별개 차원의 설계 완성도 문제다.

## 강점

구조, 증거, 범위 절제의 3가지 측면에서 잘 설계되었다.

### 1. 문서 구조가 선형적으로 설계됨

README 에서 "의사결정자용 요약"을 가장 빠른 경로로 제공하고, 00 -> 05 의 순서가 의사결정 -> 근거 -> 현황 -> 목표 -> 계획 -> 리스크로 자연스럽게 흐른다. Golden Principle #4 (결론 우선)를 충실히 따른다.

### 2. 근거 기반 서술

- 파일 수, 라인 번호, 외부 문서 링크가 본문에 고정되어 있다.
- 01은 Codex 공식 문서를 섹션별로 구분해 인용한다.
- 02는 현 저장소의 구체적 파일/라인을 참조한다.

이 때문에 리뷰어가 "이 주장은 어디서 왔나"를 추적하기 쉽다.

### 3. 범위 절제

- 00 §6과 05 §6 두 곳에서 "이것은 설계 패키지이지 구현이 아니다"를 명시한다.
- 05 §6 "의도적 비범위"는 다음 단계 작업자에게 경계를 분명히 전달한다.

의사결정 문서에서 **무엇을 하지 않을지를 명시하는 것**은 실제 구현자에게 매우 큰 도움이 된다.

### 4. 리스크 구조화

- R1~R5 가 severity + 이유 + 대응으로 형식이 일관된다.
- R1 공식 surface 오해와 R2 manual 과신을 high로 분리한 판단이 합리적이다. 두 리스크 모두 "설계 전제 자체를 무너뜨리는" 위험이기 때문이다.

### 5. 보수적 전환 원칙

04 §5의 "한 단계에서 surface 하나만 크게 바꾼다"는 회귀 범위 통제 관점에서 모범적이다. 일괄 교체가 아닌 병행 전환 후 점진 삭제 전략은 현재 duplication 규모(143 파일)에 적합하다.

## 주요 이슈 (High)

Phase 0 승인 전에 보완을 강력히 권장하는 3가지 이슈다.

### H1. 공유 SSOT 저장 위치가 "예시"로 남아 있다

**위치**: [03 §2](03-target-architecture.md) 목표 구조 트리

**문제점**:
- 03 §2 의 `src/shared/manuals/` 트리 바로 아래에 "위 구조는 예시이며, 핵심은 공유 SSOT가 .claude 밖에 존재해야 한다는 점이다"라고 명기되어 있다.
- 그런데 README "의사결정자용 요약"의 선행 과제 3개 중 1번째는 바로 "공유 문서 SSOT의 저장 위치 확정"이다.
- 즉 **가장 중요한 결정이 본 설계 패키지에서 이루어지지 않았다**.

**왜 중요한가**:
- Phase 1 "공유 SSOT 추출"의 첫 단계가 바로 이 경로 결정이다.
- 경로가 확정되지 않으면 Phase 1~6 전체 일정을 산정할 수 없다.
- 의사결정자 입장에서는 "무엇을 승인하는가"가 모호해진다.

**제안**:

02 또는 03에 아래 형식의 후보 경로 비교표를 추가한다.

```
| 후보 경로 | 장점 | 단점 | 영향받는 영역 |
|-----------|------|------|---------------|
| src/shared/ | 소스 트리 내부, 생성기 접근 용이 | claude/codex와 형제 관계로 의미 모호 | setup.js 경로 추가 |
| docs/shared/ | 문서 성격 명확 | 생성기가 docs 경로를 읽는 관례 없음 | docs-generate.js 변경 |
| 별도 패키지 | 버전 분리 가능 | 패키지 관리 오버헤드 증가 | pnpm workspace 재구성 |
```

그 다음 03 §2에서 1개를 선택하고 "예시" 표현을 제거한다.

### H2. Codex 공식 surface 링크의 검증 기록이 없다

**위치**: [01 §1](01-official-surface-and-constraints.md) 전체

**문제점**:
- 01은 `developers.openai.com/codex/...` URL 5종을 인용해 plugin / AGENTS.md / Skills / Custom agents / Hooks / Commands 각각의 경계를 확정한다.
- 본 설계의 **전제 전체가 이 링크들의 내용에 의존**한다.
- 그런데 문서 작성일(2026-04-21) 기준으로 링크가 유효한지, 인용된 내용이 현재 공식 문서와 일치하는지 확인 기록이 없다.

**왜 중요한가**:
- R1 리스크가 이미 이를 지적하지만 (severity: high, "plugin/agents/hooks 경계를 잘못 잡으면 전체 구조가 다시 뒤틀린다"), 정작 R1의 예방책인 링크 검증이 누락되어 있다.
- Codex는 상대적으로 신규 surface라 공식 문서 자체가 빠르게 변한다. 본 설계가 반영한 시점의 snapshot이 중요하다.

**제안**:

01 말미에 "공식 문서 스냅샷" 섹션을 신설하고 다음을 기록한다.

```
| 링크 | 확인일 | 인용 섹션 | 발췌 요약 |
|------|-------|-----------|-----------|
| developers.openai.com/codex/plugins | 2026-04-21 | "Structure" | skills, apps, MCP servers, assets 구조 인용 |
| developers.openai.com/codex/guides/agents-md | 2026-04-21 | "Discovery" | ~/.codex/AGENTS.md, repo root AGENTS.md 순서 인용 |
| ... | ... | ... | ... |
```

또는 더 가볍게는, Phase 0 완료 조건에 "공식 링크 5종 재확인 (책임자: X, 기한: Y)"을 추가한다.

### H3. "중복"의 정량 정의가 부재하다

**위치**: [02 §2](02-current-state-audit.md) + [04 Phase 6](04-migration-plan.md)

**문제점**:
- 02 §2 에는 파일 수만 표기되어 있다 (162 vs 143).
- 그런데 정작 중요한 것은 **143 중 몇 개가 진짜 runtime 차이이고 몇 개가 복제/재진술인가**다.
- 04 Phase 6의 완료 조건은 "src/codex 는 차이 저장소가 되고 복제 저장소가 아니게 됨"이다. 이 표현은 정성적이라 "달성 여부" 판정이 불가능하다.

**왜 중요한가**:
- Phase 6 착수 시점에 "중복 판정 기준"을 새로 만들어야 한다면 작업이 크게 지연된다.
- 의사결정자 입장에서 "몇 파일이 제거 대상인가"가 불분명하면 인력 배정이 곤란하다.
- 중복을 너무 적게 보면 작업이 작아 보이고, 너무 많이 보면 리스크가 과대평가된다.

**제안**:

Phase 0 완료 전에 `src/codex` 143 파일을 다음 3분류로 정리한 부속 자료를 첨부한다.

```
| 분류 | 정의 | 예상 파일 수 | Phase 6 처리 |
|------|------|-------------|-------------|
| A. 단순 복제 | src/claude와 본문이 거의 동일 | ? | 삭제, shared manual 참조 |
| B. 표현 차이 | 본문 구조는 같고 Codex 용어로 재진술 | ? | 삭제 후 shared manual 단일화 |
| C. runtime 차이 | Codex 고유 제약/구현이 반영됨 | ? | src/codex 유지, shared에서 참조 |
```

이 분류표가 있으면 04 Phase 6 완료 조건을 다음처럼 정량화할 수 있다.

> "A+B 카테고리 파일의 shared manual 이동 완료 및 src/codex 에서 삭제. C 카테고리만 src/codex에 잔존."

## 중간 이슈 (Medium)

Phase 0 승인 후 구현 초반에 정리해도 괜찮은 이슈들이다.

### M1. R5 severity 재평가 필요

**현재**: [05 §3 R5](05-verification-and-risks.md) "사용자 경험 악화" severity: medium

**문제점**:
- claude-kit 다운스트림 프로젝트들은 `/dev-*`, `/plan-*`, `/copy-*` 를 주된 진입점으로 사용한다.
- 본 설계의 최종 모습은 "skill 중심 진입"이다 (01 §1.6, 03 §3.2).
- 이는 **단순한 용어 변경이 아니라 전체 UX 패러다임 전환**이다.

**제안**:
- R5 severity 를 **medium -> high** 또는 "medium-high"로 재평가한다.
- 대응 방안에 "router skill 이 기존 용어(`/dev-feature`, `/plan-screen` 등)를 alias 로 흡수" 조항을 추가한다.
- 04 Phase 3 (Codex plugin 축소) 완료 조건에 "기존 command alias 흡수율 100%"를 추가한다.

### M2. pairing-registry / exception-registry 의 미래가 불명

**위치**: [02 §4.3](02-current-state-audit.md) 에서 장점으로만 언급, 03/04에서는 사라짐

**문제점**:
- 현재 `scripts/` 에 `pairing-registry.json`, `exception-registry.json`, `audit-pairing.js` 등이 존재한다.
- 02는 이들을 현재 구조의 장점으로 꼽는다.
- 그런데 03 목표 구조와 04 마이그레이션 계획 어디에도 이 메타 자산의 향후 역할이 언급되지 않는다.

**의문**:
- manual-first hybrid 로 전환하면 pairing 추적은 누가 담당하나?
- Phase 3/6 에서 이 자산은 삭제 대상인가, 진화 대상인가?

**제안**:

03 § 5 "무엇이 사라지고 무엇이 남는가" 표에 다음 행을 추가한다.

```
| pairing-registry, exception-registry | ??? (유지/진화/삭제 중 택1) |
```

그리고 04 Phase 3 또는 Phase 6 수행 항목에 해당 자산의 처리 방침을 명시한다.

### M3. 용어 혼용

본 패키지 내에서 유사한 개념이 5종 이상의 용어로 혼재한다.

| 발견된 용어 | 출현 문서 |
|------------|-----------|
| `manual-first hybrid` | README, 00, 03 |
| `공통 매뉴얼` | 00 |
| `shared manual` | 03, 04 |
| `공유 매뉴얼` | README, 00 |
| `공유 SSOT` | README, 00, 02, 05 |
| `공유 manuals` | 03 |

**문제점**:
- 의사결정자가 "공유 SSOT"와 "공유 매뉴얼"이 같은 것인지 확신할 수 없다.
- 구현자가 "shared manual"과 "공유 SSOT"의 파일 경로를 같은 곳으로 해석할지 확신할 수 없다.

**제안**:

README 또는 00에 용어 정의 블록을 추가한다.

```
## 용어 정의

- Canonical term: shared manual (공유 매뉴얼)
- 동의어: 공유 SSOT, 공통 매뉴얼, shared SSOT
- 정의: Claude 와 Codex 양쪽이 참조하는 단일 설명 저장소. 저장 경로는 03 §2 에서 확정.
```

이후 본문에서는 가급적 canonical term 으로 통일한다.

### M4. 검증 질문의 측정 방법 부재

**위치**: [05 §1](05-verification-and-risks.md)

**문제점**:

## 경미 이슈 (Low)

### L1. setup.js 라인 인용 중 일부 미검증

02 에서 인용한 `scripts/setup.js:660`, `scripts/setup.js:689` 는 본 리뷰 시점에 spot-check 하지 못했다. 다른 인용(40, 610)이 모두 정확했으므로 높은 확률로 정확하겠지만, Phase 0 승인 전에 빠르게 확인하는 것을 권장한다.

예:
- Phase 4 (.codex/agents 도입) 와 Phase 5 (Hook 정리) 는 surface 가 다르므로 독립 작업 가능
- Phase 1 (공유 SSOT 추출) 와 Phase 2 (AGENTS.md 재구성) 중 일부는 병렬 가능

**제안**: 04 에 Mermaid 또는 ASCII 의존성 다이어그램을 1개 추가해 크리티컬 패스를 시각화한다.

### L3. 시점 의존 정보의 재확인 주기 없음

01 §1.5 "PreToolUse 는 현재 Bash interception 위주" 같은 주장은 Codex 공식 surface 가 변하면 즉시 무효화된다.

**제안**: 01 말미에 "이 문서의 공식 surface 주장은 분기별 재확인 대상" 같은 문구를 추가한다.

## 종합 판단

**이 설계 패키지는 Phase 0 조건부 승인 대상이다.**

설계의 골격 (manual-first hybrid, 공식 surface 우선, `.claude` 의존 배제, 보수적 전환) 은 견고하다. 현재 저장소 실태 (162 vs 143) 를 정확히 반영했고, 공식 Codex 문서 구조를 체계적으로 인용했으며, 리스크 구조도 잘 잡혀 있다.

다만 **H1~H3 의 3가지 공백은 Phase 1 착수 시 곧바로 발목을 잡는다**. 공유 SSOT 경로가 없으면 Phase 1 을 시작조차 못 하고, 공식 링크 검증 기록이 없으면 설계 전제 자체가 흔들리며, 중복 정량 정의가 없으면 Phase 6 완료를 선언할 수 없다.

따라서 권장 순서는 다음과 같다.

```
[현재 상태: draft]
     |
     v
[H1/H2/H3 보완]  <- 작성자가 수행, 수 시간 ~ 수일
     |
     v
[의사결정자 Phase 0 최종 승인]
     |
     v
[Phase 1 공유 SSOT 추출 착수]
```

중간 이슈 (M1~M4) 와 경미 이슈 (L1~L3) 는 Phase 0 를 막지 않으므로 구현 초반에 점진 반영하면 된다.
