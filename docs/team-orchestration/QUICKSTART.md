# Team AI 실행 가이드

> 스킬은 `/plan-idea`처럼 혼자 일하는 전문가 한 명을 부르는 것이다.
> 팀 AI는 전문가 여러 명이 동시에 일하는 프로젝트 팀을 꾸리는 것이다.

---

## 스킬 vs 팀 AI

| | 스킬 (`/command`) | 팀 AI |
|---|---|---|
| **비유** | 전문가 1명 호출 | 프로젝트 팀 구성 |
| **실행** | `/plan-idea "검색 필터"` | `/orchestrate` 또는 "팀으로 해줘" |
| **동시성** | 순차 (1개씩) | 병렬 (최대 3개 동시) |
| **적합한 작업** | 단일 Feature, 단일 리뷰 | 3+ Feature 병렬, 대규모 리팩토링 |
| **복잡도** | 낮음 (한 줄 실행) | 중간 (팀 구성 + 작업 배분) |

### 언제 팀을 쓰나?

- Feature가 **3개 이상**이고, 일부가 독립적으로 진행 가능할 때
- **조사 + 구현 + 테스트**를 동시에 돌리고 싶을 때
- 대규모 **리팩토링**에서 여러 모듈을 동시 수정할 때

### 언제 팀이 필요 없나?

- Feature 1~2개를 순차 처리할 때 → 스킬로 충분
- 같은 파일을 여러 명이 수정해야 할 때 → 충돌 발생, 스킬이 안전
- 간단한 버그 수정 → 스킬 또는 서브에이전트

## 방법 1: `/orchestrate` (가장 쉬움, 추천)

모든 팀 구성을 자동으로 해준다. 사용자는 "무엇을 할지"만 말하면 된다.

### 기본 사용

```
/orchestrate
```

위 명령을 실행하면:
1. Claude가 현재 작업 계획(`prompt_plan.md` 등)을 분석
2. 작업을 자동으로 쪼개고 의존성을 파악
3. 팀을 구성하고 작업을 배분
4. 병렬로 실행하고 결과를 수집

### 옵션

```
/orchestrate --type feature     # Feature 개발 (기본: 구현자2 + 테스터1)
/orchestrate --type bugfix      # 버그 수정 (조사자1 + 수정자1)
/orchestrate --type refactor    # 리팩토링 (분석자1 + 구현자1 + 검증자1)
/orchestrate --type review      # 코드 리뷰 (보안1 + 성능1 + 품질1)
/orchestrate --parallel 2       # 동시 작업 수 제한 (기본: 3)
/orchestrate --dry-run          # 실행 안 하고 계획만 미리보기
```

### 실행 예시

```
사용자: 주문 조회 API와 정산 내보내기 기능을 동시에 개발해줘
       /orchestrate --type feature

Claude: === Team Orchestration ===
        Tasks: 6 | Waves: 2 | Teammates: 3

        Wave 1 (병렬):
          Implementer-1: 주문 조회 API (도메인 모델 + 엔드포인트)
          Implementer-2: 정산 내보내기 (엑셀 생성 + 다운로드)
        Wave 2 (Wave 1 완료 후):
          Tester: 통합 테스트 + 코드 리뷰

        팀을 생성하고 작업을 시작합니다...
```

실행 중에는 진행 상황 테이블이 표시된다:

```
Task                          │ Owner          │ Status
──────────────────────────────┼────────────────┼────────
주문 도메인 모델               │ Implementer-1  │ done
주문 API 엔드포인트            │ Implementer-1  │ >> 진행중
정산 엑셀 생성                 │ Implementer-2  │ done
정산 다운로드 엔드포인트        │ Implementer-2  │ >> 진행중
통합 테스트                    │ Tester         │ 대기
코드 리뷰                      │ Tester         │ 대기
```

## 방법 2: 자연어로 요청

팀 관련 키워드를 사용하면 Claude가 자동으로 팀을 구성한다.

```
"팀으로 이 3개 작업을 병렬로 처리해줘"
"에이전트 팀을 구성해서 프론트엔드와 백엔드를 동시에 개발해줘"
"보안 리뷰, 성능 리뷰, 코드 품질 리뷰를 동시에 돌려줘"
```

Claude가 적절한 팀 구성을 제안하고 실행한다.

## 방법 3: 수동 팀 구성 (고급)

완전히 제어하고 싶을 때 직접 팀을 만든다.

### Step 1: 팀 생성

```
"order-feature라는 팀을 만들어줘"
```

Claude가 `TeamCreate`를 실행하여 팀 파일과 작업 디렉토리를 생성한다.

### Step 2: 작업 정의

```
"다음 작업을 등록해줘:
1. 주문 도메인 모델 작성
2. 주문 API 엔드포인트 구현 (1번 완료 후)
3. 주문 테스트 작성 (2번 완료 후)"
```

Claude가 작업을 `TaskCreate`로 등록하고 의존성을 설정한다.

### Step 3: 팀원 스폰

```
"구현자 에이전트와 테스터 에이전트를 스폰해줘"
```

Claude가 `Agent` 도구로 팀원을 생성한다. 각 팀원은 자기 작업을 시작한다.

### Step 4: 모니터링

실행 중 팀원들이 자동으로 상태를 보고한다:

```
[Implementer-1] 주문 도메인 모델 완료. 다음 작업으로 이동합니다.
[Tester] 주문 도메인 모델에 대한 단위 테스트 작성 중...
```

사용자는 언제든 개입할 수 있다:

```
"Implementer-1의 현재 상태를 알려줘"
"Tester에게 엣지 케이스 테스트도 추가하라고 전달해줘"
```

### Step 5: 완료 + 정리

모든 작업이 끝나면:

```
"팀을 종료해줘"
```

Claude가 각 팀원에게 `shutdown_request`를 보내고 팀 리소스를 정리한다.

## 핵심 규칙 3가지

### 1. 파일 소유권 분리

**같은 파일을 두 팀원이 동시에 수정하면 안 된다.** 나중에 쓴 내용이 먼저 쓴 내용을 덮어쓴다.

```
Implementer-1: src/orders/       (주문 관련 파일 전담)
Implementer-2: src/settlement/   (정산 관련 파일 전담)
Tester:        tests/            (테스트 파일 전담)
```

`/orchestrate`를 사용하면 파일 소유권이 자동으로 분배된다.

### 2. Hub-and-Spoke 통신

모든 보고는 **팀 리더(=메인 세션)**를 통한다. 팀원끼리 직접 대화하지 않는다.

```
팀원 A ──보고──> 리더 ──지시──> 팀원 B
       (직접 A→B 통신 없음)
```

### 3. 리더는 코딩하지 않는다

팀 리더(메인 세션)는 조율만 한다. 직접 코드를 작성하면 컨텍스트가 소진된다. 모든 구현은 팀원에게 위임한다.

## 제약 사항

| 제약 | 설명 |
|------|------|
| **동시 팀원 최대 3명** | 리더 1 + 팀원 3 = 총 4 세션 |
| **파일 충돌 주의** | 같은 파일 동시 수정 불가 |
| **컨텍스트 미상속** | 팀원은 리더의 대화 내용을 모름 (CLAUDE.md만 공유) |
| **중첩 팀 불가** | 팀원이 또 다른 팀을 만들 수 없음 |

## 문제 해결

### "팀원이 멈춘 것 같아요"

팀원은 매 턴 후 **idle** 상태가 된다. 이것은 정상이다. 메시지를 보내면 깨어난다.

```
"Implementer-1에게 계속 진행하라고 전달해줘"
```

### "파일 충돌이 발생했어요"

1. 충돌이 발생한 팀원을 일시 중지
2. 리더가 `git status`로 상태 확인
3. 파일 소유권을 재배분 후 재개

### "작업이 너무 오래 걸려요"

```
"현재 진행 상황을 요약해줘"
"Implementer-2의 작업을 취소하고 다른 접근 방식으로 해줘"
```

### "중간에 팀을 해체하고 싶어요"

```
"팀을 종료해줘"
```

미완료 작업은 리더가 이어서 단독으로 처리하거나, 새 팀을 구성할 수 있다.

## 요약: 어떤 방법을 쓸까?

| 상황 | 추천 |
|------|------|
| 처음 써보는 경우 | `/orchestrate` |
| 3+ 독립 작업을 병렬로 | `/orchestrate --type feature` |
| 빠른 조사 + 수정 | `/orchestrate --type bugfix` |
| 세밀한 제어가 필요 | 방법 3 (수동 팀 구성) |
| 단순 작업 1~2개 | 팀 불필요, 스킬(`/dev-feature`) 사용 |
