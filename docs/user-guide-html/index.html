claude-kit 실제 사용 가이드

이 문서는 claude-kit의 기획 파이프라인, 개발 파이프라인, Codex 전환 흐름을 실제 작업 순서로 따라갈 수 있게 정리한 HTML 문서입니다. 제품 소개용 랜딩 페이지가 아니라, 처음 설치한 사용자와 maintainer가 반복해서 확인하는 작업 문서입니다.

핵심 기준

Claude Code의 commands, agents, skills, hooks, rules는 Codex에서 그대로 복사해 쓰는 대상이 아닙니다. Codex에서는 skills, custom subagents, AGENTS.md, hook config 같은 공식 surface에 맞게 다시 표현합니다.

이 문서가 답하는 질문

01

기획은 어디서 시작하나?

/plan-idea에서 시작해 PRD, wireframe, design, bridge까지 어떤 순서로 이어지는지 설명합니다.

02

개발은 무엇을 기준으로 하나?

Feature Package를 TDD 구현, 검증, 리뷰, 커밋으로 넘기는 /dev-* 흐름을 설명합니다.

03

Codex에서는 무엇이 달라지나?

src/claude 자산을 src/codex authoring source로 전환하는 기준을 설명합니다.

빠른 시작

처음에는 전체 기능을 외우려고 하지 말고, 현재 작업이 기획인지 개발인지 Codex 전환인지 먼저 고르면 됩니다. 그다음 해당 entry command를 실행하고, 생성된 산출물을 확인합니다.

첫 10분 체크리스트

  1. 설치 output 확인

    .claude/, .agents/skills/, .codex/가 현재 프로젝트에 맞게 생성되어 있는지 확인합니다.

  2. 작업 흐름 선택

    아이디어 정리라면 /plan-idea, 승인된 PRD 기반 개발이라면 /plan-bridge 또는 /dev-feature, Codex 전환이라면 /kit-convert로 시작합니다.

  3. 산출물 위치 확인

    기획 산출물은 .plans/, Claude authoring source는 src/claude, Codex authoring source는 src/codex를 기준으로 확인합니다. 기획 파일 이동 규칙은 산출물 lifecycle을 봅니다.

  4. 검증을 한 번 끼워 넣기

    개발 작업은 /dev-verify, Codex 전환 작업은 /kit-validate 또는 /kit-audit로 누락과 drift를 확인합니다.

언제 무엇을 쓰나

claude-kit은 하나의 큰 명령으로 모든 일을 처리하기보다, 목적별 pipeline을 작게 나눕니다. 아래 표에서 지금 상황에 가장 가까운 줄을 고르면 됩니다.

상황 시작 명령 다음에 확인할 것
아이디어를 기록하고 정리해야 함 /plan-idea idea record, 태그, 문제 정의
여러 Feature를 하나의 상위 목표로 묶어야 함 /plan-epic Epic Brief, Children Features, phase roadmap
아이디어 우선순위를 판단해야 함 /plan-screen Go / Hold / Kill, RICE 또는 5축 평가
PRD와 화면 구조가 필요함 /plan-prd, /plan-wireframe 승인된 PRD, screen map, 요구사항 매핑
Claude Code Design으로 디자인 프롬프트가 필요함 /plan-design .plans/design/{slug}/, Claude Design URL
Google Stitch로 디자인 통합을 보강하고 싶음 /plan-stitch .plans/stitch/{slug}/, mapping, validation
개발로 넘길 준비가 필요함 /plan-bridge Feature Package, dev handoff, TASK 분해
승인된 기능을 구현해야 함 /dev-feature, /dev-run 구조 SSOT, TDD 루프, 검증 명령
Claude 기능을 Codex용으로 전환해야 함 /kit-convert src/codex, pairing registry, validation report

기획 파이프라인

plan domain은 아이디어를 실제 개발 가능한 package로 다듬는 흐름입니다. 핵심은 “좋은 아이디어”를 바로 구현하지 않고, 문제 정의, PRD, 화면 구조, 디자인 산출물, 개발 handoff를 순서대로 확보하는 것입니다.

상세 문서로 이동

각 /plan-* 명령의 agents, skills, hooks, rules는 Planning 기능 reference에서 확인하고, 생성·이동·archive 경로는 산출물 lifecycle에서 확인합니다.

대표 흐름

0/plan-epic

선택 사항. 여러 Feature를 묶는 상위 목표와 phase roadmap을 관리합니다.

1/plan-idea

아이디어를 구조화하고 backlog 또는 inbox에 등록합니다.

2/plan-screen

RICE 또는 5축 평가로 Go, Hold, Kill 판단을 제안합니다.

3/plan-draft

First Pass 문서를 만들고 Lite 또는 Standard 경로를 판단합니다.

4/plan-prd

문제, 목표, 요구사항, UX, 기술, 리스크를 담은 PRD를 작성합니다.

5/plan-wireframe

ASCII 또는 Mermaid 기반으로 화면 구조와 사용자 흐름을 정리합니다.

6A/plan-design

Claude Code Design용 2단계 프롬프트와 design package를 생성합니다.

6B/plan-stitch

필요 시 Google Stitch 기반 통합, 매핑, 검증 산출물을 생성합니다.

7/plan-bridge

기획 산출물을 개발자가 실행할 수 있는 Feature Package로 넘깁니다.

8/plan-archive

완료된 기획/개발 산출물을 archive bundle로 정리합니다.

기획 단계의 완료 기준

  • 아이디어는 승인 전까지 개발 pipeline으로 넘기지 않습니다.
  • PRD는 문제, 목표, 요구사항, UX, 기술 제약, 리스크를 포함해야 합니다.
  • Wireframe은 PRD의 주요 요구사항과 화면이 서로 연결되어야 합니다.
  • Design 또는 Stitch 산출물은 /plan-bridge가 개발 handoff를 만들 수 있을 정도로 충분해야 합니다.

디자인 분기: /plan-design과 /plan-stitch

/plan-design과 /plan-stitch는 경쟁 관계가 아닙니다. 기본은 Claude Code Design을 위한 /plan-design이고, Google Stitch 기반 보강이 필요할 때 /plan-stitch를 선택합니다. 프로젝트에 따라 둘 중 하나만 쓸 수도 있고, 둘 다 순차적으로 쓸 수도 있습니다.

명령 역할 주요 입력 주요 산출물
/plan-design Claude Design용 wireframe/high fidelity 프롬프트 생성 승인된 PRD, wireframe .plans/design/{slug}/prompt-01-wireframe.md, prompt-02-highfidelity.md, manifest.md
/plan-stitch Google Stitch 활용 또는 PRD/Wireframe 통합 검증 보강 승인된 PRD, wireframe, 필요 시 design 산출물 .plans/stitch/{slug}/mapping.md, context.md, validation.md

허용되는 디자인 경로

기본 경로 PRD -> /plan-wireframe -> /plan-design -> /plan-bridge

Claude Code Design 중심으로 충분할 때 사용합니다.

Stitch 선택 경로 PRD -> /plan-wireframe -> /plan-stitch -> /plan-bridge

Google Stitch를 중심으로 디자인 통합과 검증을 진행할 때 사용합니다.

순차 보강 경로 PRD -> /plan-wireframe -> /plan-design -> /plan-stitch -> /plan-bridge

Claude Design 산출물을 만든 뒤 Stitch로 추가 통합이 필요할 때 사용합니다. 이 경우 sequential reason을 남깁니다.

개발 파이프라인

dev domain은 승인된 Feature Package를 코드 변경으로 전환합니다. 좋은 개발 흐름은 “코드를 많이 쓰는 것”보다 작업 범위를 작게 잡고, 실패 테스트와 검증 결과를 증거로 남기는 것입니다.

표준 개발 흐름

단계 명령 목적 완료 기준
구조 확인 /dev-architecture 구조 SSOT와 feature binding 확인 수정 위치와 boundary가 설명됨
기능 계획 /dev-feature PRD를 Feature Overview와 TASK로 전환 작업 단위와 acceptance criteria가 있음
구현 /dev-run TDD Red-Green-Refactor 루프 수행 관련 코드와 테스트가 함께 변경됨
검증 /dev-verify 테스트, 빌드, lint, 요구사항 검증 실행한 명령과 결과가 보고됨
리뷰 /dev-review, /dev-security-review 회귀, 보안, 문서 누락 확인 남은 리스크와 후속 작업이 분리됨
마감 /dev-commit, /dev-commit-push-pr 커밋 또는 PR 준비 논리적 변경 단위로 기록됨

개발에서 자주 쓰는 에이전트와 스킬

구조 판단에는 dev-architect, 구현에는 dev-implementer, 리뷰에는 dev-code-reviewer, 보안 점검에는 dev-security-reviewer, 검증에는 dev-verify-agent를 우선 확인합니다.

Codex 병행 사용

Codex는 Claude runtime 파일을 그대로 읽지 않습니다. 같은 기능 identity를 유지하더라도 Codex에서는 공식 runtime surface에 맞는 자산으로 표현해야 합니다.

기능 Claude 쪽 표현 Codex 쪽 표현 주의점
명령 .claude/commands/*.md Codex skill 파일 복사가 아니라 사용자 entrypoint를 skill로 재표현합니다.
에이전트 .claude/agents/*.md .codex/agents/*.toml 역할, trigger, output shape를 좁게 정의해야 합니다.
스킬 .claude/skills/*/SKILL.md .agents/skills/*/SKILL.md 대체로 재사용 가능하지만 Codex runtime 기준 검증이 필요합니다.
훅 .claude/hooks/*.js hook pair 또는 skip 공식 hook surface와 플랫폼 제한을 먼저 확인합니다.
작업 지침 .claude/rules/*.md AGENTS.md synthesis 일반 지침은 Codex exec-policy rule과 구분합니다.
source와 runtime을 구분하세요

src/codex는 Codex runtime output이 아니라 Codex용 authoring source입니다. 실제 runtime output은 설치 또는 emitter 단계에서 .agents/skills, .codex/agents, AGENTS.md 등으로 생성됩니다.

Claude to Codex 변환 기준

현재 conversion-first 기준은 src/claude -> conversion -> src/codex입니다. 처음 만들 때 두 target을 동시에 생성하는 것이 아니라, 이미 존재하는 Claude 자산을 분석하고 Codex authoring source로 전환하는 흐름이 1차 목표입니다.

기본 매핑

Claude source kind Codex target 변환 판단
agent subagent 좁은 역할, 명시적 산출물, read-heavy 작업이면 우선 변환합니다.
command skill 사용자 entrypoint를 Codex skill workflow로 재작성합니다.
skill skill 형식과 runtime 전제만 검증하고 재사용합니다.
hook hook-pair 또는 codex-skip 이벤트, matcher, 플랫폼 제한을 만족할 때만 변환합니다.
instruction-rule AGENTS.md synthesis 행동 지침으로 요약하고 exec-policy rule로 자동 변환하지 않습니다.

변환 단계

  1. Inventory

    src/claude 전체 자산을 수집하고 identity를 붙입니다.

  2. Classify

    auto-convert, convert-with-review, skip을 판단합니다.

  3. Generate

    src/codex에 conversion-generated authoring source를 생성합니다.

  4. Review

    semantic drift, runtime gap, 수동 보정 필요 영역을 확인합니다.

  5. Validate

    schema, pairing, parity, skip reason을 검증합니다.

문제 해결

문제가 생기면 generated output만 고치지 말고 source, template, emitter, runtime output 중 어디가 실제 원인인지 먼저 나눠 봅니다.

증상 확인 위치 다음 행동
설치 후 명령이 보이지 않음 .claude/commands, profile, setup output postinstall 또는 setup 재실행 여부를 확인합니다.
기획 산출물이 개발로 이어지지 않음 /plan-bridge, Feature Package, routing metadata PRD, wireframe, design 또는 stitch 산출물이 충분한지 확인합니다.
Codex 기능이 Claude와 다르게 보임 src/codex, .agents/skills, .codex/agents Codex는 direct copy가 아니라 target-specific authoring source를 사용한다는 점을 확인합니다.
hook이 실행되지 않음 event, matcher, platform support Codex hook 지원 범위 또는 codex-skip 사유를 확인합니다.
문서와 실제 파일이 다름 docs/guide, docs/codex-compatibility, source tree HTML이 gateway 문서인지, source guide가 갱신되어야 하는지 구분합니다.
